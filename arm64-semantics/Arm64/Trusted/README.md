# `Arm64/Trusted/`: The AArch64 Trusted Computing Base

Everything under `Arm64/Trusted/` (plus the top-level umbrella [`Arm64.lean`](../../Arm64.lean), which imports [`Arm64/Trusted.lean`](../Trusted.lean)) is **trusted** (`Role::Spec`, Lake library `Arm64`, definitions only, 0 theorems). Nothing here may import `ProofLib`, `Examples`, `Challenges`, Mathlib, or any test module (`Arm64.Testing.*`, `Examples.Testing.*`); `check-trust-guards` enforces this. Library layering is `Arm64 < ProofLib < Examples < Testing` (plus `Challenges`, which may import only `Arm64` and `Examples`).

Spec files should `import Arm64` rather than individual modules: it brings in the ISA semantics, the `Init`-only semantic specification vocabulary in [`Spec/`](Spec/) (separation logic, Hoare triples, subroutine hooks, ASCII decimal formatting/parsing), and the surface specification DSLs and literal macros in [`Surface/`](Surface/) (`c_spec` / `rust_spec`, `c_type_spec`, `hex_words%`, `ascii!` / `asciic!` / `asciiCode!`). Spec files must not import `ProofLib` (it contains no `Role::Spec` modules), so they cannot use the untrusted typed ABI combinators (`Spec.split`, ...) or the `ProofLib/LibcHooks.lean` allocator model; a campaign that needs such a helper defines a small local one in its own `Spec.lean`. For the design principles, the per-definition lookup table, and the list of untrusted components that validate this code, see [`Arm64/README.md`](../README.md); for how it is tested, see [`Arm64/TESTING.md`](../TESTING.md) and [`Arm64/Testing/`](../Testing/README.md).

For the list of supported instruction families and how atomics, barriers, hints and system registers are modeled sequentially, see [`ISA/README.md`](ISA/README.md).

## Why the spec vocabulary is trusted: Pollack consistency

A kernel-checked proof only shows that the theorem *as elaborated* holds. Whether it means what an auditor thinks it means depends on how the surface syntax in `CaseStudies/<Campaign>/Spec*.lean`, `Examples/{UnitTests,CaseStudies}/<Campaign>/Spec*.lean`, and `CaseStudies/<Campaign>/Theorems/*.lean` expands, and that syntax is built from the definitions in [`Spec/`](Spec/) and [`Surface/`](Surface/). A bug in `c_spec` / `rust_spec` expansion (e.g. dropping a `requires` clause, or not tying `returns` to `X0`) or in `subroutineHook` would make a spec weaker than it reads while the proof still goes through. So these definitions are kept small, contain no proofs, and are reviewed as part of the TCB. To see what they add up to, read the guided tour [`Arm64/Testing/Tours/SpecAdequacyTour.lean`](../Testing/Tours/SpecAdequacyTour.lean): in the style of Iris's adequacy theorem, it proves that a `c_spec` / `c_type_spec` `subroutine_ok` theorem implies a statement about `Arm64.Steps`, registers, and memory bytes alone, with no `SepProp`, `∗`, or `↦` in it. Lemmas, tactics, and convenience combinators *about* them are untrusted and live in `ProofLib/`:
