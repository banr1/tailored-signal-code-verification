# `ProofLib/ProofTerm/`: proof-term size and kernel hot-spot control

Tools for the cost that comes *after* a proof elaborates: the Lean kernel re-checks every proof
term, and a few innocent-looking steps can make it unfold large concrete definitions (code images,
symbol tables, specifications) for tens of seconds. Everything here is untrusted
(`Role::Proof`): the commands only read the environment and call the kernel on existing terms; the
tactics only add `let` definitions, change the goal up to definitional equality, or clear
hypotheses. None of them can make a false statement provable.

| You want to … | Use | File |
|---|---|---|
| find which declarations of a module are slow **in the kernel** | `#kernel_profile_module Mod.Prefix` | `KernelProfile.lean` |
| time specific declarations (with their `_proof_*` / `decide +kernel` helpers) | `#kernel_profile d₁ d₂` | `KernelProfile.lean` |
| fail the build when a declaration exceeds a kernel budget | `#kernel_profile! …`, `#kernel_profile_module! …` | `KernelProfile.lean` |
| find **where** inside one proof the kernel spends its time | `#kernel_hotspots d` | `KernelProfile.lean` |
| statically flag proof shapes that make the kernel unfold big terms | `#kernel_lint d₁ …`, `#kernel_lint_module Mod.Prefix` | `Lint.lean` |
| share a repeated large sub-term of the goal | `kfold`, `kfold?` | `KFold.lean` |
| drop hypotheses that cannot matter before an expensive tactic | `clear_dead`, `clear_dead!`, `clear_dead?` | `ClearDead.lean` |

Import: `import ProofLib.ProofTerm` (or the single file). Tests:
`Examples/Testing/ProofLib/ProofTerm.lean`. Synthetic benchmarks (built by `lake build Testing`):
`Examples/Testing/ProofLib/ProofTerm/Bench.lean` (kernel hot spots) and `BenchTactics.lean`
(`clear_dead`, `kfold`). Driver for whole modules:
`scripts/kernel-profile <Module> [<ModulePrefix>] [<threshold_ms>]`.

## Workflow: profile → localise → fix → re-profile

1. **Profile.** Write a scratch file (never commit it) that imports the slow module, then:

   ```lean
   import My.Slow.Module
   import ProofLib.ProofTerm
   set_option proofLib.kernelProfile.thresholdMs 2000
   #kernel_profile_module My.Slow.Module
   ```

   Output, largest first (auxiliary declarations such as `foo._proof_1` or the lemma generated by
   `decide +kernel` are counted under `foo`). Real output on three theorems of a crypto-verification
   producer module (`#kernel_profile d₁ d₂ d₃`, threshold 0):

   ```text
   [kernel_profile] scope=explicit decls=3 over_threshold=3 threshold=0.0 ms total=61198.0 ms
   [kernel_profile] Swarm.Refinement.Decrypt.pollProtoStore_ok_of_inMem_ext kernel=22178.4 ms (value 22178.3 ms + type 0.1 ms) share=36.2% aux_decls=13
   [kernel_profile] Swarm.Refinement.Decrypt.pollProtoTrust_ok_of_inMem_ext kernel=19736.8 ms (value 19736.7 ms + type 0.1 ms) share=32.3% aux_decls=13
   [kernel_profile] Swarm.Refinement.Decrypt.pollProtoSave_ok_of_inMem_ext kernel=19282.8 ms (value 19282.8 ms + type 0.1 ms) share=31.5% aux_decls=13
   ```

   This re-runs the kernel only; nothing is re-elaborated, so it is much cheaper than
   `-Dtrace.profiler=true` on the whole file (which needs `-DElab.async=false` for per-declaration
   numbers).

2. **Localise.** `#kernel_hotspots My.foo_ok` walks the proof term the way the kernel does and
   re-checks, one at a time, every place where the kernel must decide a definitional equality: an
   application argument whose type is not syntactically the parameter type, a `let` value, a type
   that must be reduced to a Π-type, and the final "inferred type ≡ declared type" check. It prints
   the most expensive sites. Real output (abridged) for the slowest theorem above:

   ```text
   [kernel_hotspots] Swarm.Refinement.Decrypt.pollProtoSave_ok_of_inMem_ext kernel=17999.4 ms aux_decls=13 ... sites_timed=3892 over_min=1 (min 100 ms)
   #1 15253.2 ms  argument 1 of `id` — decide (kernel evaluates the Decidable instance)
      expected: decide (widgetCode.fnOff pollProtoSaveName + 255584 = widgetCode.fnOff "__rustc::__rust_dealloc") = true
      actual: true = true
      only in expected: [Arm64.Program.fnOff, WidgetVerification.widgetCode, Decidable.decide, HAdd.hAdd, …]
      only in actual: []
   ```

   Read it as: "the kernel spent 15 s checking that argument; the two types differ by the
   constants listed, so it had to evaluate / unfold them" (here: a `by decide` autoParam makes the
   kernel run the symbol-table lookup `fnOff`). The headline names the tactic that
   usually produces that shape (`rw`/`simp` cast, `change`/`dsimp` cast, `decide`, plain argument).
   Site times are single, isolated re-checks and vary from run to run (an independent re-run of
   this exact walk reported the same site at 20.0 s instead of 15.3 s): use them to rank sites,
   not as exact costs.
   Options: `proofLib.kernelHotspots.top` (default 8 sites), `proofLib.kernelHotspots.minMs`
   (default 10 ms).

3. **Fix** with one of the patterns below, then re-run step 1 on the same statement.

### Fix patterns

- **Generic transport lemma** (the kernel never compares two big concrete terms). When a proof
  only moves between two presentations of the same specification (adds a pure conjunct, reorders,
  unfolds a wrapper), state a lemma generic in the parts that do not matter (`P : α → State → Prop`,
  `Rest : α → SepProp`, `post`) and prove the concrete statement as an instance:

  ```lean
  -- slow: the kernel unfolds `bigSpec` and compares the unfolded body with the goal
  theorem foo_ok (h : subroutine_ok prog addr (bigSpec.inImage img)) : subroutine_ok prog addr {...} := by
    intro x R s0 hpc hrun hm hsp; refine h x R s0 hpc hrun ?_ hsp
    dsimp only [Spec.inImage, bigSpec]; exact ...
  -- fast: same statement, through a lemma that never mentions `bigSpec`
  theorem transport_generic {P : α → State → Prop} {Rest : α → SepProp} {post} ... := ...
  theorem foo_ok' (h : ...) : subroutine_ok prog addr {...} :=
    transport_generic (P := fun x s => ...) (Rest := fun x => ...) h ...
  ```

- **Discharge address/offset side conditions with the lemma set, not by evaluation.** A side
  condition like `fnOff code name + k = fnOff code stub` should be closed by
  `simp only [arm64_norm]` (or by the generated `*_fnOff_*` lemmas) so the proof term is a chain of
  lemma applications. `decide` / `by decide` autoParams and hand-written `rw` chains that leave a
  `Decidable` instance or a literal comparison to the kernel make it run the symbol-table lookup.

- **Bind repeated sub-terms** with `kfold` before a tactic that would copy them into many proof
  steps, and **clear dead hypotheses** with `clear_dead` before tactics that scan the context.

## `#kernel_lint`

`#kernel_lint d` inspects the elaborated proof term and reports (only `cast-unfolds-heavy` calls the
kernel, to confirm a candidate by timing):

- `decide-on-heavy` — a `Decidable.decide … = true` check (from `decide`, `by decide` autoParams)
  whose proposition mentions a *heavy* constant: a constant tagged `@[kernel_heavy]`, or a
  definition whose body has at least `proofLib.kernelLint.heavyNodes` distinct nodes (default 2000;
  generated code images and symbol tables qualify), or one that mentions such a definition up to two
  definitions deep. Lean core / `Std` constants are never heavy.
- `cast-unfolds-heavy` — a definitional-equality site (an `id` cast from `change` / `dsimp` /
  `show`, an `Eq.mpr` cast from `rw`, a mismatched application argument, a `let` value, or the
  final type check) whose two types differ around a heavy constant (one side only, or as a sibling
  argument of the differing sub-term, e.g. `fnOff code name` vs `fnOff code "<literal>"`), *and*
  whose isolated kernel re-check takes at least `proofLib.kernelLint.castMs` (default 1000 ms).
  Most such sites are cheap, so this rule is confirmed by timing; set `castMs 0` to see every
  candidate.
- `rw-on-heavy` (opt-in: `set_option proofLib.kernelLint.staticRw true`) — every `rw` step whose
  rewritten term mentions a heavy constant. Static and noisy; the expensive `rw` steps are already
  reported by `cast-unfolds-heavy`.

`#kernel_lint! …` errors on any finding (use as a gate). `decide-on-heavy` and `rw-on-heavy` are
static, so they give the same verdict on every run; `cast-unfolds-heavy` depends on kernel timing,
so a site whose re-check takes close to `castMs` can flip between runs or machines. For a
timing-free gate, set `proofLib.kernelLint.castMs 0` (every candidate is reported). Extend the
heavy set with `attribute [kernel_heavy] myBigTable` (a global tag that only this lint reads; it
changes nothing for elaboration or the kernel).

## `kfold`

`kfold` repeatedly binds the closed sub-term with the largest saving `(occurrences − 1) × size` as
`let kf_i := t` and replaces its occurrences in the goal (a definitional change). `kfold?` logs what
it folded and the goal's tree size before and after. Options: `kfold (minSize := 24) (maxLets := 16)`.
It is useful before tactics that would otherwise copy a big concrete term into many proof steps; it
does not change what the kernel must *unfold*, only how often it meets copies.
Measured caveat (`BenchTactics.lean`): on a goal with eight copies of a 400/800-element literal,
`kfold; simp only` elaborates 8-10× *slower* than plain `simp only` (116 vs 14 ms, 229 vs 23 ms),
because Lean already shares the repeated term in memory. Use it only after measuring a gain.

## `clear_dead`

`clear_dead` keeps the hypotheses in the cone of influence of the goal (hypotheses that mention a
free variable of the goal, transitively, plus closed facts) and clears the rest; `clear_dead!` is
the aggressive term-level variant (only equations reachable from the goal by left-to-right
rewriting survive). `clear_dead?` / `clear_dead!?` print the equivalent `clear h₁ h₂ …`;
`clear_dead keep h₁ h₂` protects hypotheses. If a later tactic fails after `clear_dead!`, use
`clear_dead` or add the needed hypothesis to `keep`.

## Limits

- Kernel timings are wall-clock and machine-dependent; compare like with like.
- `#kernel_hotspots` re-checks each site in isolation (no shared kernel caches), so site times rank
  sites but can sum to more than the declaration total. Sites inside `Prop`-irrelevant positions
  that the kernel skips by proof irrelevance may be reported although the real check skipped them.
- Theorem bodies of `module`-system files are only visible through `import all`.
